# 审计结果展示与用户选择

## 展示要求

- 采用"漏斗式"分层展示，主屏行数只与模块数 + 问题类型数挂钩，与接口总数解耦。
- 开头先给结论句：审计 N 个接口、需改 M 个，P0 ×a / P1 ×b / P2 ×c，集中在哪些文件与问题类型。
- 只列"需要增改"的接口；已有断言且合理的接口汇总一句"无需改动：xxx、xxx"，不展开。
- 同 route 的多个场景调用只列一次；同一模式的问题合并为一条"模式 + 建议 + 涉及接口列表"，不逐条重复理由。

## 漏斗四层

1. **统计句（≤3 行）**：接口总数 / 需改数 / 各优先级计数。
2. **模块看板（行数 = 文件数）**：文件 | 总数 | 需改 | P0 | P1 | P2 | 主要问题，按需改数降序。
3. **问题簇表（行数 = 问题类型数）**：问题类型 | 计数 | 涉及文件 | 统一建议，同一模式只写一次。
4. **明细（按需下钻）**：默认只展开 P0 全列；P1 每文件 top 3、其余记"同模式 +N"；P2 只列接口名。规模大时全量明细落报告文件（如 `report/audit-YYYY-MM-DD.md` 或 CSV），消息内只给文件链接，编号以报告文件为准。

## 阈值阶梯

| 需改接口数 | 展示方式 |
|---|---|
| ≤8 | 全量明细内联（按文件分组，表内 P0 → P2 排序） |
| 9–40 | 统计句 + 汇总表（编号\|接口\|问题类型\|优先级）+ P0/P1 明细，P2 合并为一行"顺带可改"清单 |
| 41–200 | 统计句 + 模块看板 + 问题簇表 + 仅 P0 明细，P1 每文件 top N |
| >200 | 统计句 + 模块看板 + 问题簇表 + P0 代表例；全量明细落报告文件 |

明细表按优先级排序（P0 → P1 → P2），理由不超过一句话，真实返回截断 ≤60 字符；汇总表列保持最简。

## 问题类型

- 缺断言：只有默认三断言，建议增加。
- 假断言：传了 params 但 route 无 extraAssertions，实际未校验。
- 建议修改：已有断言但可增强 / 与返回不符。

## 用户选择

结尾给出选择方式，未确认前不落 apiTest 代码：

- 回复"全部应用"＝应用所有建议（或仅 P0/P1，视用户确认范围）；
- 回复"模块名"（如 item.js / testmanager.js）＝只应用该文件建议；
- 回复"编号列表"（如 1,3,5）＝只应用指定项（接口多时编号以报告文件为准）。
